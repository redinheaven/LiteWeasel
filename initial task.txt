你是一名精通 Windows C++、TSF（Text Services Framework）、Direct2D/DirectWrite/DirectComposition 和系统级性能优化的资深工程师。项目是 `rime/weasel` 的 fork：https://github.com/redinheaven/Lite_weasel

目标：在低配旧机器上（ThinkPad X1 Carbon 5th Gen (20HR, KabyLake-U)、X220 这类内存小、CPU 低压低频的机器）让打字丝滑。具体包括：
- 第一个字出得快
- 每次按键延迟低
- 宿主程序不被输入法拖死

动手之前先读 `AGENTS.md`（规范）和 `PROGRESS.md`（进度）。

版本：v2（2026-11-19），根据可行性评估和用户决定修订。

## 顶层取舍原则

1. **第一个字的出字速度优先于省内存。** 延迟和内存冲突时选低延迟。
2. **先测量，再优化。** 每项性能改动都要有前后对比数据。
3. **任务书和代码不一致时，以代码为准**，并把差异记进 `PROGRESS.md`。

## 核心工程约束

- 修改前先用 grep 或 read 精确定位。严禁破坏 COM 接口签名、ABI 兼容性、IPC 消息格式和高 DPI 缩放逻辑。
- 每完成一个阶段，x64 和 x86 都要编译通过，且没有新增错误。回复里要给出修改摘要和自测方法，并更新 `PROGRESS.md`。
- 涉及高风险并发、IPC 协议或架构重构的改动，先出设计方案和影响面分析，经确认后再写代码。
- 构建环境：装了 VS2022 的台式机，用 `weasel.sln` + `build.bat`，xmake 作为备选。

## 第 1 阶段：WARP 软件渲染验证（已实现，只验证）

现状：`WeaselUI/d2d.cpp` 已经优先用 `D3D_DRIVER_TYPE_WARP` 创建 D3D11 设备，失败时退回硬件。交换链用 `CreateSwapChainForComposition` 配合 DComp。

用户决定：**不改代码，保留退回硬件的逻辑。**

1. 用 Process Explorer 或 ListDLLs 检查组过字的宿主进程，确认没有加载显卡驱动的用户态 DLL（`igd*`、`igc*`、`nvwgf2um*`、`atiumd*` 等）。只出现 `d3d10warp.dll` 才算正常。
2. 记下 WARP 路径下每帧的绘制耗时。
3. 第 1 阶段之后绘制压力全在 CPU 上，所以要把阴影和模糊的开销单独测出来，为第 5 阶段第 1 项提供数据。

## 第 2 阶段：UI 资源懒加载（已取消）

用户决定：**保持现在的预热机制**，也就是 `WeaselTSF/CandidateList.cpp` 的 `StartUI` 里的 `Refresh()` + `Hide()`。理由是第一个字快比省内存更重要。

要求：后面任何改动都不能削弱这个预热，也不能把 D2D 资源的创建推迟到第一次绘制时。

## 第 3 阶段：进程和线程调度优先级

1. 在 `WeaselServer/WeaselServer.cpp` 的 `_tWinMain` 初始化阶段，调用 `SetPriorityClass(GetCurrentProcess(), ABOVE_NORMAL_PRIORITY_CLASS)`。
   不用 HIGH，因为在双核低压 CPU 上它可能饿死其他进程。
2. 部署和维护是在 Server 进程内跑的（`RimeWithWeasel.cpp` 的 `start_maintenance`）。要在维护线程上单独降低优先级：
   `SetThreadPriority(THREAD_PRIORITY_BELOW_NORMAL)`。评估是否还要加 `THREAD_MODE_BACKGROUND_BEGIN` 来降低 I/O 优先级。
   需要先确认维护线程是在哪里创建的（librime 内部还是 weasel 侧）。
3. `WeaselDeployer.exe` 启动时设成 `BELOW_NORMAL_PRIORITY_CLASS`。
4. 验证方法：在部署期间连续输入，和基准数据对比按键延迟。

## 第 4 阶段：IPC 防卡死（先出方案，确认后再改）

现状（`WeaselIPC/PipeChannel.cpp`）：
- 服务端没运行时，`CreateFile` 会立刻失败，这个场景本来就很快。
- `_Connect` 在管道一直 BUSY 时，会无限循环调用 `WaitNamedPipe(500)`。
- `_Receive` 和 `_WritePipe` 是同步的 `ReadFile`/`WriteFile`，没有超时。服务端卡住时，宿主 UI 线程会一直挂着。

方案要覆盖这几点：
1. 给连接重试设上限：总时长或次数封顶，超过就快速失败，然后异步拉起服务端。是否用 `OpenMutex` 探测作为辅助手段，由方案评估决定。
2. 读写改成 overlapped I/O，配合 `WaitForSingleObject` 超时和 `CancelIoEx`。超时阈值建议 150–300ms，不用 50ms，因为冷启动和部署后的第一个键很容易超过 50ms，会导致吞键。
3. 超时后的协议恢复：断开重连，或者把迟到的回包读掉丢弃，同时重建或校验 session。
4. 熔断：连续超时后，在一段时间内直接放行按键，不再逐个等待。
5. 影响面分析：哪些 TSF 回调需要同步拿到结果（比如 `OnTestKeyDown`），超时后应该返回什么。

## 第 5 阶段：其他提速项（按第 0 阶段的测量结果排序）

1. **阴影和模糊**：在 WARP 下测出它们的开销，必要时提供轻量阴影或默认关闭。可以同时在文档里提醒用户设置 `shadow_radius: 0`。
2. **去掉写完就 Flush**：`PipeChannel.cpp` 的 `_WritePipe` 写完后调用了 `FlushFileBuffers`，紧接着又同步读回包，等于重复等待。要验证去掉后语义不变。
3. **统计每个按键的 IPC 往返次数**：看能不能合并请求。
4. **交换链尺寸**：改成只放大不缩小，或者预留余量，避免每个按键都 `ResizeBuffers`。
5. **文字测量缓存**：`StandardLayout.cpp` 等布局代码每次都对所有文本调用 `GetTextSize`。对编号、翻页符号、`mark_text` 这类不变的内容做缓存。
6. **字体回退**：避免每次按键都临时查找字体，尤其是彩色 emoji 字体。
7. **唤醒预热**：服务端监听 `WM_POWERBROADCAST`（PBT_APMRESUMEAUTOMATIC），唤醒后在后台预读词库，避免唤醒后第一个字卡顿。
8. **文档类建议**（写进 README，不改代码）：给 Defender 设排除项、精简 Rime 方案（Lua、多词库、OpenCC、page_size）、用 Process Lasso 设置优先级和关闭核心停放。
